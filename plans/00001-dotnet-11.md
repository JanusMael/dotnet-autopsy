# 00001 — Move the tooling to .NET 11

**Status:** approved 2026-11-16

## Goal

The canonical base image, CI, the shared report apps and the two `.csproj`
hosts build on .NET 11 (SDK 11.0.100, runtime 11.0.0, GA 2026-11-10), with
the parity GOLDEN gate still byte-exact **on the SDK that CI actually uses**,
and all three per-case flows proven against real dumps, traces and gcdumps by
checks that can fail. This lands before anything else is pushed. Nothing is
pushed or released without an explicit go-ahead.

## Decisions

Decisions 2, 3, 9, 10 and 11 were made or confirmed by the developer on 2026-11-16.

1. **Diagnostic tools stay at 10.x.** Nothing newer exists. They are installed
   unpinned, so they pick up an 11.x release automatically when one ships.
2. **`dotnet-monitor` 9.0.0 → 10.0.5.** It runs natively on 11, which
   removes the tool's dependence on the roll-forward shim. Keep
   `ENV DOTNET_ROLL_FORWARD=Major` anyway: it costs nothing and covers the
   next SDK major the same way it covered this one.
3. **Moving from LTS to STS is accepted.** Both are supported until Nov 2028.
4. **Captured parity fixtures stay as they are.** The `10.0.8` and
   `10.0.300` strings in `*/parity/fixtures/**` (and echoed in the goldens)
   are inputs recorded from .NET 10 artifacts. They remain valid test inputs.
5. **The goldens must not change.** If an app compiled for .NET 11 produces a
   different byte, that's a finding to investigate, not a golden to
   regenerate.
6. **The file server version moves on its own.** `FILESERVER_VERSION=latest`
   resolves to `2026.11.16` at the next build whatever this plan does. Doc
   examples pinned to `2026.9.2` stay valid as examples and are not changed
   here.
7. **TraceEvent stays at 3.2.3.** 4.0.0 is a major bump on a parity-gated
   dependency and gets its own change.
8. **Historical text stays.** `CHANGELOG.md` entries describing past releases
   keep their ".NET 10" wording.
9. **One branch carries everything that goes up next.** `feat/dotnet-11` is
   cut from `docs/progress` (which holds the unpushed `PROGRESS.md` commit),
   so PR A carries `PROGRESS.md`, this plan and the upgrade together.
10. **The sos success checks are fixed in PR A, locally and in CI.** Both the
    local smoke and CI's sos checks can currently pass on a broken analysis,
    which is the exact failure this upgrade risks. The fix covers
    `sos/smoke.sh`'s own hook, `rot-check.yml`'s amd64 sos job and the
    in-image `SMOKE_TEST` in `sos/dotnet-sos.dockerfile`. The shared
    `sc_status_check` and the trace and gcdump rot-check jobs are left
    unchanged. (Developer chose option (a) on 2026-11-16, after being told the
    smoke alone doesn't run in CI.)
11. **No `global.json`.** CI pins the SDK in `ci.yml`, Docker builds use the
    image's SDK, and step 7 checks the local SDK by hand.

## Steps

### Branch and plan

1. `git switch -c feat/dotnet-11` from `docs/progress`. On approval, commit
   this plan on its own before any implementation.

### PR A — canonical

2. `common/base.dockerfile`: `DOTNET_SDK_IMAGE` default → `sdk:11.0` (both
   ARG sites); `DOTNET_MONITOR_VERSION` → `10.0.5` (both sites); update the
   roll-forward comment to say it now guards future majors rather than the
   pinned monitor; ".NET 10" → ".NET 11" in the descriptive comments and the
   generated `/analysis/sources/README`.
3. `.csproj` TFMs: `common/FileServerHost` and `trace/TraceTriage`
   `net10.0` → `net11.0`.
4. CI:
   - `ci.yml` (the parity gate) `setup-dotnet` `10.x` → `11.0.x`;
   - `rot-check.yml` `setup-dotnet` `10.0.x` → `11.0.x` and its step name;
   - `publish.yml` MCR pre-warm ref → `sdk:11.0`.
5. Scripts: `common/lib/smoke-common.sh` and `demo.sh` default image →
   `sdk:11.0`. Their `net${SDK_MAJOR}.0` TFMs are already derived from the SDK
   and need no change. Fix `sos/smoke.sh` `content_asserts` (decision 10):
   the `dotnet-dump` exec must fail when `dotnet-dump` does (no exit status
   swallowed by `head`), and the hook must require `/analysis/status.json` to
   show `status` = `success`, `dump_fidelity` = `full-or-triage` and a
   `dac_source` other than `fetch-failed`.
5a. CI's sos checks (decision 10):
   - `rot-check.yml` amd64 sos job: replace "success or partial" with the same
     three `status.json` requirements, and print the throwaway dump's
     `runtime_version` so the CI log shows which runtime was analyzed (the
     runner's preinstalled `dotnet` decides it).
   - `sos/dotnet-sos.dockerfile` `SMOKE_TEST=1`: capture the
     `dotnet-dump analyze` output and fail unless it contains an
     `OS Thread Id:` row, rather than trusting the exit code.
6. Docs describing the current toolchain: `README.md` (including the
   `DOTNET_MONITOR_VERSION` default `9.0.0` → `10.0.5` in the build-args
   table), `CONTRIBUTING.md`, the three `RUNBOOK.md`s, the per-image dockerfile
   banners, the `.cs` header comments, `run-parity.sh`'s requirements line,
   and the `sos/delve-lldb.sh` example path. Confirm that the
   "`dotnet publish file.cs` defaults to NativeAOT" claim still holds on 11
   before rewording it.

### Verification (before the PR is opened)

Each check names what proves it. **If any check fails, stop: commit nothing
further, report the failure and the options, and wait.** No partial upgrade is
pushed.

7. Parity: `dotnet --version` prints `11.0.100`, then
   `bash common/parity/run-parity.sh {sos,trace,gcdump}` passes byte-exact.
8. Build the base and each per-case image and run each `smoke.sh`. The fixed
   sos smoke enforces `status` = `success` (which `finalize_status` sets only
   when SOS produced real rows and the dump isn't `degraded`),
   `dump_fidelity` = `full-or-triage` and a working `dac_source`; also confirm
   by hand that `runtime_version` starts `11.0.`. **Prove the new check can
   fail:** run the hook's `status.json` check against a copy that says
   `status: partial` and confirm a non-zero exit. Build the sos image once
   with `--build-arg SMOKE_TEST=1` and confirm the in-image check passes and
   prints the `OS Thread Id:` evidence. For trace and gcdump the smokes
   already assert content.
9. Cross-version, by hand, because `sos/smoke.sh` always regenerates its own
   dump with a single SDK image: in a throwaway `sdk:10.0` container, capture
   a dump with the same FailFast recipe as `sos/smoke.sh`; copy it out to the
   repo root as `smoke-core.dump` (covered by `.gitignore`'s `*.dump`);
   `docker build -f sos/dotnet-sos.dockerfile --build-arg DUMP_FILE=smoke-core.dump`
   on top of the 11 base from step 8; run it bound to `127.0.0.1:5550`; read
   `/analysis/status.json` with `json-get` and apply step 8's checks, expecting
   a `runtime_version` starting `10.0.`. Then remove the container and the
   dump, and confirm `git status` doesn't list it.
10. File server starts clean on the new base: no DataProtection or HTTP_PORTS
    warnings, `/` redirects to `/analysis`, `RELEASE.txt` records the resolved
    version.
11. Push and open PR A only on the go-ahead. CI must be green: parity ×3, with
    the `setup-dotnet` log showing an 11.0 SDK, and rot-check amd64+arm64,
    with the amd64 sos job reporting `status: success` and logging the dump's
    runtime version.

### PR B — Chainguard (branch `chore/chainguard-regen-dotnet-11`, after A merges)

12. `./chainguard/generate.sh -y --force`; update `chainguard/README.md`
    (the ".NET 10 only" caveat and the roll-forward rationale for
    `dotnet-monitor`). Build with `./chainguard/build.sh` and run the toolchain
    smoke. Kept separate because `chainguard-isolation.yml` requires it.

### Release (only on an explicit instruction)

13. `CHANGELOG.md` entry, update `PROGRESS.md`, CalVer tag per
    `CONTRIBUTING.md` § Cutting a release.

## Done when

- Parity is byte-exact for all three flows on an 11.0 SDK, locally and in CI.
- All three smokes pass on the 11 base. The fixed sos smoke passes for an
  11.0 dump and a 10.0 dump, and has been shown to fail on a `partial`
  status. CI's rot-check sos job requires `status: success`, and the
  in-image `SMOKE_TEST` requires real SOS output.
- PR A and PR B are green in CI.
- No remaining ".NET 10" text describes the current toolchain, apart from
  historical CHANGELOG entries and captured fixtures.

## Out of scope

TraceEvent 4.0.0; file server version pins in docs; a published Chainguard
image; branch-protection changes; tightening the shared `sc_status_check`
and the trace and gcdump rot-check jobs; pinning the runtime of CI's
throwaway sos dump.
